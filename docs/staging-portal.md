# Постоянный тестовый портал для приёмки

Рабочий портал остаётся на прежнем адресе `http://192.168.70.9:8001/`. Тест устанавливается в отдельную папку и по умолчанию слушает порт 8002. Его устанавливают из отдельной ветки/архива, без слияния в `main` и без обновления работающего портала. Наличие этой инструкции не означает, что тест уже установлен на вашем сервере.

Вход первоначально разрешён одному владельцу. Его логин однозначно сопоставляется с активным пользователем и компанией в снимке рабочей базы. Для теста задаётся **свой новый пароль**; пароль Windows не нужен. Остальные учётные записи остаются в снимке для проверки ролей через «Работать как пользователь», но самостоятельно войти на тест не могут, даже если им задать пароль через карточку пользователя. В будущем состав проверяющих можно расширить отдельным изменением правил доступа.

## Что разделено

У теста свои база SQLite, загруженные файлы, приватные акты, секретный ключ, cookie сессии/CSRF, статические файлы, зависимости Python, журналы, резервные копии и задание Windows `YDS Portal Test`. Cookie имеют уникальные имена: одновременный вход на одном IP с портами 8001 и 8002 не завершает рабочую сессию.

Тестовый сервер не запускает менеджер учебных копий и фоновые обмены. LDAP отключён. Подключения 1С и сохранённые SMTP-реквизиты удаляются **только из снимка**, очередь приглашений отменяется, копии сессий и пароли очищаются. Реальная отправка почты заменена dummy backend, запуск почтового потока отключён. Регистрация, подключение AD/1С, приглашения и учебные копии дополнительно заблокированы на уровне middleware. Страница обновления в тестовом режиме обращается только к отдельному обработчику теста; производственная очередь обновлений не используется. Переключение ролей владельцем разрешено.

Тест не сбрасывается в 07:00. Его данные сохраняются после перезапуска компьютера и при обновлении кода теста. Базу с теста в прод не переносят.

## Первая установка одной командой, без архива

В PowerShell **от имени администратора на сервере** выполните следующий блок. Вместо `SHA_ИЗ_PR` укажите полный SHA подготовленной версии из pull request, а не `main`:

```powershell
$revision = 'SHA_ИЗ_PR'
$installer = Join-Path $env:TEMP 'install-yds-test.ps1'
Invoke-WebRequest -UseBasicParsing -Uri "https://raw.githubusercontent.com/Hvidsmen/gpr_systerm/$revision/ops/bootstrap-staging.ps1" -OutFile $installer
powershell.exe -NoProfile -ExecutionPolicy Bypass -File $installer -Revision $revision
```

Вручную скачивать и распаковывать ZIP не нужно. Скрипт получает **точный коммит** в отдельную папку. Если установлен Git, используется отдельный checkout; без Git файлы загружаются напрямую с GitHub и сверяются с Git blob SHA-1, включая бинарные документы. Архивы не используются ни в одном варианте. Имена файлов, ссылки, полнота дерева и отсутствие пересечения с рабочими путями проверяются до установки. Незавершённая загрузка удаляет только созданную для неё временную папку.

Папка работающего портала по возможности определяется из задания `YDS Portal` (только чтение). Если это не удалось, скрипт спросит её. По умолчанию рядом создаётся `YDS-Test`. После неудачной первоначальной настройки можно повторить ту же команду с тем же SHA: загрузчик проверит, что в папке остался неизменённый код этой версии, а тестовая база, ключи и рабочая конфигурация ещё не созданы. В этом случае он продолжит установку без повторного скачивания. Папки с данными, изменённым кодом, ссылками или посторонними файлами не используются и не перезаписываются. Для другого размещения передайте `-Root` и `-ProductionRoot` в команду запуска.

Далее установщик спросит ваш логин и новый **отдельный тестовый пароль**. На тесте допускается любой непустой пароль до 4096 символов, в том числе `admin`. Проверки длины и сложности при смене пароля отключены только в настройках тестовой среды. Пароль вводится скрыто; он не попадает в аргументы команд или открытый файл. Если пароль пустой, слишком длинный или подтверждение не совпало, установщик предложит ввести его снова, не завершая установку. Рабочие `.env`, ключи и виртуальное окружение не копируются.

После успешной установки адрес теста по умолчанию — `http://192.168.70.9:8002/`. Над каждой страницей должен появиться баннер «ТЕСТОВЫЙ ПОРТАЛ», номер версии и ссылка на рабочий портал. До запуска установщика на вашем сервере этот адрес нельзя считать уже работающим.

Для явного выбора параметров:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File $installer -Revision $revision `
  -Root C:\YDS-Test -ProductionRoot C:\YDS-Prod -OwnerLogin YOUR_LOGIN -Port 8002 -Hosts 192.168.70.9
```

При необходимости можно по-прежнему распаковать ZIP точного коммита в отдельную папку и запустить `INSTALL_GPR_TEST.cmd`; это дополнительный способ, а не требование.

Нужна уже установленная Windows-версия с `.runtime/installed.json` и `.runtime/current.json`. Установщик использует базовый интерпретатор установленного Python, но создаёт собственное окружение теста. Зависимости фиксированы в `requirements.staging.lock` (включая основной lock-файл). Если Python недоступен, передайте `-PythonExecutable`. Если приватные акты лежат по нестандартному `ACTUATION_FILES_ROOT`, передайте их папку параметром `-ActuationRoot`.

Снимок БД делается через SQLite Backup API с источником `mode=ro` и проверкой целостности. Рабочая БД не мигрируется и не заменяется. Документы копируются отдельными файлами. Они и БД не образуют единую транзакцию: загрузка нового документа одновременно с копированием может потребовать повторного копирования при следующей подготовке снимка. Ссылки, junction и совмещение рабочих/тестовых путей запрещены. Нужны место для полной копии данных и права чтения источника.

Повторная установка поверх существующего теста отказывается перезаписывать данные. Если подготовка не завершилась, готовая конфигурация не публикуется; журнал — `.runtime/prepare.log`. Установщик не останавливает и не перерегистрирует задания `YDS Portal` / `YDS Portal Update`. Он создаёт только `YDS Portal Test` и правило `YDS-Portal-Test` для выбранного порта во внутренней подсети, профили Domain/Private. Это программная изоляция двух установок на одном сервере; отдельная виртуальная машина даст дополнительную изоляцию ресурсов и прав ОС.

## Управление только тестом

Из папки теста, PowerShell администратора:

```powershell
.\ops\control-staging.ps1 -Action Status
.\ops\control-staging.ps1 -Action Stop
.\ops\control-staging.ps1 -Action Start
```

Либо `CONTROL_GPR_TEST.cmd -Action Status`. Остановка ждёт завершения запросов. При превышении времени обновление не начинается. Скрипт проверяет, что задание теста принадлежит выбранной папке. Рабочие задания не затрагиваются.

## Обновление теста кнопкой в браузере

Откройте на порту **8002** «Администрирование → Обновление тестового портала» или ссылку в жёлтом баннере. Адрес: `/accounts/admin/update/`.

1. Нажмите **«Проверить обновления»**. Появятся установленная и доступная версии.
2. Нажмите **«Обновить тестовый портал»**. Устанавливается именно показанный коммит ветки `codex/staging-portal-20261102`, даже если ветка позже продвинется.
3. Дождитесь сообщения **«Тестовый портал обновлён и доступен»**. При перезапуске страница сама восстанавливает связь. Вкладку можно закрыть: задание сохранено на сервере.

Обновление доступно только владельцу теста, вне режима «Работать как пользователь». Повторное задание во время обновления отклоняется. GET страницы и опрос статуса не скачивают код и не запускают обновление. Выбор версии подписан, привязан к установке и текущей версии и действует один час. Нет расписания автоматической установки новых коммитов и переноса данных с теста в прод.

Задание `YDS Portal Test` теперь содержит постоянный обработчик, который перезапускает только дочерний HTTP-процесс теста. Скачивание идёт при работающем тесте; затем обработчик завершает его запросы, применяет штатную процедуру резервного копирования и миграций и проверяет ответ новой версии на локальном тестовом порту. Письма и обмены остаются отключены. Задачи Windows рабочего портала не изменяются.

**Для старой установки без этой кнопки нужен один переход через PowerShell** по инструкции ниже. Переустанавливать тест, пересоздавать его базу или запускать bootstrap поверх готовой папки не нужно. После перехода следующие версии устанавливаются кнопкой.

## Свежие рабочие данные на тесте

На той же странице откройте блок **«Данные с основного портала»**. Он отделён от обновления кода.

1. Прочитайте предупреждение: текущие тестовые база, документы и приватные акты будут заменены.
2. Отметьте **«Подтверждаю замену тестовой базы и документов свежими рабочими данными»**.
3. Нажмите **«Обновить данные с основного портала»**. Тест остановится на время копирования и проверки. Основной портал продолжает работать.
4. После восстановления связи нажмите **«Войти в тестовый портал»** и войдите прежним отдельным тестовым паролем. Дата последнего обновления данных появится в этом блоке.

Рабочая SQLite читается через Backup API в режиме `mode=ro`, документы копируются из сохранённых при установке исходных папок. Текущая тестовая версия кода, секретный ключ, instance и отдельный хеш пароля владельца сохраняются. В свежем снимке заново сопоставляется логин владельца и назначается роль администратора. Скопированные рабочие пароли, сессии, SMTP/1С и активные учебные копии очищаются тем же штатным механизмом, что при создании теста. Если владелец больше не определяется однозначно, обновление отменяется до замены данных.

Свежая база проходит миграции и проверку установленным кодом в отдельной временной папке. Перед заменой создаётся `.runtime/backups/<id>/database.sqlite3`; при успешной замене туда же переносится целиком прежняя папка `data` со всеми документами, а также сохраняются `staging.json` и `secret.key`. Старые тестовые данные не удаляются из резервной копии. Неудачная подготовка оставляет текущие данные на месте; ошибка публикации восстанавливает прежние базу, документы и конфигурацию вместе. Прерывание непосредственно во время замены либо ошибка восстановления блокирует HTTP до проверки администратором. Журнал замены — `.runtime/staging-refresh-transaction.json`.

Обновление кода и данных использует одну очередь: одновременно выполняется одна операция. Подтверждение замены подписано и привязано к экземпляру, версии кода и поколению данных, действует один час и не подходит для повторной замены после успешного обновления. GET страницы, расписание 07:00 и проверка версии данные не заменяют.

Если код обновлён из сборки с первым браузерным обновлятором, но старый постоянный обработчик ещё работает, кнопка замены данных недоступна с пояснением. Один раз остановите и запустите **только** `YDS Portal Test`, либо примените эту сборку через штатную PowerShell-команду обновления теста. После запуска нового обработчика функция включается. Производственные задания трогать не нужно.

При восстановлении после неудачной замены данных используйте сохранённую папку `data`, прежний `staging.json` и при необходимости `secret.key` из указанной резервной копии, пока тест остановлен. После проверки уберите журнал замены, маркер `.runtime/staging-recovery.json` и файл задания `.runtime/staging-update.json`, затем запустите только тест. Файлы и SQLite не образуют общую транзакцию на рабочем портале: при одновременном изменении исходных документов может потребоваться повторное копирование.

## Первое включение кнопки и ручное обновление до конкретного кандидата

Скачайте ZIP нового проверяемого коммита. Внутреннее имя корня архива GitHub должно соответствовать указанному SHA; архив ветки `main.zip` не принимается.

```powershell
.\ops\control-staging.ps1 -Action Update -Archive C:\Downloads\candidate.zip -Revision EXACT_40_CHARACTER_COMMIT_SHA
```

Скрипт останавливает **только тест**. Новый код и собственное окружение Python готовятся в `.runtime/releases/<SHA>`. Перед миграциями сохраняются снимок тестовой БД и прежняя конфигурация. Выполняются `check`, миграции и `collectstatic`; затем переключается указатель версии и запускается тестовый сервер. Рабочие база, файлы, код и задачи не обновляются.

При сбое подготовки миграций тестовая база восстанавливается из снимка, пока HTTP-сервер остановлен и удерживается блокировка. Старая конфигурация остаётся выбранной. Проверьте `.runtime/prepare.log`, затем запустите тест отдельно. После возобновления пользовательского ввода автоматически восстанавливать БД нельзя: новые данные требуют отдельного решения.

При обновлении из браузера скачивание с ошибкой оставляет текущий HTTP-процесс работающим. После обычной ошибки подготовки обработчик запускает прежнюю восстановленную версию. Журналы — `.runtime/server.log` и `.runtime/prepare.log`, состояние задания — `.runtime/staging-update.json`. Если восстановление базы не удалось либо процесс прервался в фазе `applying`, создаётся `.runtime/staging-recovery.json` и тест остаётся остановленным. Администратор сервера проверяет журнал и резервную копию `.runtime/backups/<id>/database.sqlite3`, восстанавливает только остановленную тестовую базу и её прежний `staging.json`, затем удаляет маркер восстановления и завершённый файл задания `.runtime/staging-update.json` и запускает только `YDS Portal Test`. При наличии пользовательских записей после запуска новой версии восстановление БД требует отдельного решения.

## Выпуск в прод

Приёмка на тесте не означает разрешения на выпуск. Изменения остаются в отдельной ветке и pull request. Слияние в `main` и выпуск рабочей версии требуют подтверждения конкретного релиза пользователем.

У существующего рабочего установщика есть задание `YDS Portal Update`, запускающее проверку `main` при старте компьютера. Этот установщик теста его не меняет. До перехода на утверждённые релизы нужно отдельно согласовать и выполнить изменение политики обновлений рабочего сервера. Нельзя считать его уже отключённым из-за создания теста.

## Если осталась незавершённая установка ранней версии

Ранние сборки, включая `5da256c`, требуют пароль от 12 символов. Повторный запуск их установщика не применяет изменения из нового коммита. Папку удалять не нужно.

Чтобы использовать короткий пароль, например `admin`, запустите текущий bootstrap из нужного SHA этого PR с новой отдельной папкой. Для примера, после получения `$installer` и `$revision` из раздела первой установки:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File $installer -Revision $revision -Root (Join-Path $env:USERPROFILE 'Desktop\YDS-Test-admin')
```

Старая незавершённая папка сохраняется до успешной установки новой сборки. Если тест уже установлен и имеет данные, его не нужно пересоздавать: используйте штатное обновление существующей тестовой установки. Новая установка откажется заменять уже зарегистрированное задание теста.

Короткий пароль разрешён только в тестовой среде. Введите его при установке: значение не задаётся автоматически и по-прежнему хранится хешированным. Это пароль тестового портала, а не пароль почтового ящика или Windows.
