# Работа администратора в режиме пользователя

В разделе «Пользователи» у активной обычной учетной записи есть кнопка «Войти как пользователь». Это режим с реальными действиями, не только просмотр. Он доступен администратору компании, включая суперпользователя своей компании, для локальных и AD-карточек. Пароль человека не требуется.

Права и объекты берутся у выбранного пользователя. Например, наблюдатель не может изменять данные, а диспетчер видит свои назначенные объекты. Сессия остается аутентифицированной исходным администратором; пароль и сессии выбранного человека не меняются. Над страницей показывается постоянная плашка с именами пользователя и администратора и кнопкой возврата. Возврат и начало режима принимают только POST с CSRF.

Нельзя выбрать другую компанию, другого администратора, staff/superuser или отключенную учетную запись; нельзя запускать вложенный режим. В режиме пользователя закрыты глобальная админка, управление учетными записями, вход/выход и смена пароля. Для этого сначала нужно вернуться кнопкой на плашке. Через 30 минут либо при изменении прав исходного администратора/активности/компании выбранного пользователя режим завершается. На каждой странице доступ проверяется заново.

## История

В «Пользователи → История действий под пользователями» администратор видит журнал своей компании: начало, возврат, попытки изменяющих запросов с кодом ответа, сохранение и удаление записей. Каждое изменение содержит ссылку на реального администратора и ID выбранного пользователя. Для обычных полей сохраняются старые и новые значения в AuditLog; пароли, токены, секреты, двоичные данные и большие JSON-поля не копируются в журнал. Для пакетных изменений без модельных сигналов остается запись запроса, а детали сохраняются в штатной истории соответствующего процесса.

В событиях заданий и решениях согласования с actor_name добавляется отметка «через администратора …»; события проверки сметчика содержат ID и имя фактического администратора в details. Учетная запись согласующего в бизнес-процессе остается выбранным пользователем, а журнал аудита хранит реального исполнителя. POST-тело и заголовки авторизации не журналируются. Режим не обращается к AD за паролем пользователя и не выполняет вход от его имени на контроллере домена.

Отдельных миграций эта доработка не требует. Требуется уже установленный LDAP-функционал accounts/0009 для доменных карточек.
