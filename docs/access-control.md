# Доступ к данным

Все страницы приложения, кроме входа и регистрации, требуют авторизации.
Без назначенной компании пользователь может открыть настройки профиля и выйти,
но не может читать или создавать бизнес-данные. Компанию назначает
суперпользователь через `/admin/`; она больше не создаётся автоматически.

Списки, карточки, аналитика, календарь и план/факт ограничены компанией
пользователя. При запросе чужой записи по ID возвращается 404. В формах
связанные объекты другой компании недоступны и отклоняются при проверке POST.
Массовые операции изменяют только записи текущей компании.

Админ-панель Django предназначена для глобального управления и доступна только
суперпользователям. Флаг `is_staff` и роль `ADMIN` сами по себе не дают доступа
к глобальной админ-панели. В обычных разделах приложения суперпользователь также
должен иметь компанию и видит только её данные.

Для нового обработчика используйте `CompanyScopedMixin` в generic views,
`CompanyRequiredMixin` при создании объектов и явный фильтр `company` в запросах
из собственных `get_queryset`, function views и обработчиков массовых операций.
Middleware проверяет вход и наличие компании, но не фильтрует запросы к БД.
Сохраняйте фильтр компании при переопределении queryset полей формы.

Проверки: `python manage.py test core` и `python manage.py check`.
Тесты создают отдельную тестовую БД и проверяют анонимный доступ, подмену ID,
чужие внешние ключи, аналитику и массовые операции, а также разрешённые действия
в своей компании. Для облачной среды добавьте `--settings=cloud_settings`
и используйте окружение и `PYTHONPATH`, сохранённые в инструкциях запуска.

Эта политика разделяет компании. Детальные права ролей внутри одной компании
задаются отдельно; существующие проверки согласования планов сохраняются.
