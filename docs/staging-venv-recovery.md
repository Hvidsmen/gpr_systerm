# Тайм-аут создания Python-окружения теста

Диагностический признак: обновление останавливается в `ops/staging.py:update` на `python -m venv …`, `subprocess.TimeoutExpired` через 300 секунд. Это происходит до установки зависимостей, резервной копии и миграций новой попытки. Старые успешные записи `prepare.log` не означают, что новая версия подготовлена.

Создание окружения теперь разбито на отдельные ограниченные шаги с `START` / `DONE` / `TIMEOUT` и выводом в `.runtime/prepare.log`:

1. Базовый Python запускается с `-I -m venv --without-pip` в очищенном окружении и с закрытым вводом.
2. Существующий Python теста использует поддерживаемый `pip --python` для установки pip в новый venv из wheel, поставляемого с `ensurepip`. Этот шаг не обращается к индексу пакетов и не запускает встроенный bootstrap ensurepip.
3. Проверяется `python -I -m pip --version` нового окружения.
4. В новый venv устанавливаются прежние фиксированные зависимости. Настройки доверенных сертификатов и прокси сохраняются; проверка TLS не отключается.

Тайм-аут не увеличен. Если шаг зависнет, завершается только созданный установщиком процесс и его дерево: на Windows используется его PID с `taskkill /T`, на Unix — отдельная группа процесса. Поиск и завершение процессов по имени `python.exe` не используются. Ошибка подготовки не допускает перехода к миграциям. Если Windows не даёт удалить незавершённый каталог, ошибка уборки записывается в журнал и не препятствует перезапуску выбранной старой версии теста.

Для уже установленного старого обработчика применяется однократный `ops/repair-staging.ps1` из точного SHA исправления. Он получает проверенный новый исходник до остановки, проверяет отдельную задачу `YDS Portal Test`, использует новый механизм подготовки, создаёт обычную резервную копию перед миграциями и полностью перезапускает тот же тестовый launcher. Рабочая установка не меняется. Существующие неизменяемые релизы не перезаписываются. Данные, пользователи и документы теста сохраняются; обновление базы из production не запускается.

Проверки включают настоящий offline bootstrap, изоляцию от `PYTHONHOME` / `PYTHONPATH`, остановку зависшего процесса и Windows-потомка, отказ до pip при неудаче создания, а также перезапуск старой версии при заблокированной уборке. Windows CI запускает их на Python 3.13. Опциональная интеграционная проверка `STAGING_BROWSER_TESTS=1 STAGING_RELEASE_TESTS=1 STAGING_REPAIR_INSTALL_TESTS=1` проходит полный цикл с отдельной базой и новым venv.
