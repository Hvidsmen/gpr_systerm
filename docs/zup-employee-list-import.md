# Загрузка списка сотрудников ЗУП

Администратор запускает загрузку в существующем справочнике «Сотрудники» кнопкой «Загрузить из ЗУП». Она создаёт задание общей очереди 1С; SQL SELECT выполняется Windows-обработчиком под Windows-аутентификацией настроенного подключения. Состояние и счётчики доступны в истории заданий 1С.

Загружаются ФИО, код сотрудника (поле `_Code`, отображается как табельный номер), организация, подразделение, наименование должности. По ссылке на ФИО открывается подробная карточка. Дополнительно загружаются подтверждённые структурой даты рождения/приёма/увольнения, ИНН, СНИЛС, место рождения, количество ставок, график и плановые тариф/ФОТ. Личные и платёжные поля видны только ADMIN/HR_HEAD. Фактическая зарплата и документы не загружаются. Ручное связывание по табельному номеру пока не реализовано.

Схема сверена с отчётом `029db83b-04fe-4d59-8b46-9dd7ace3c805` из текущей ЗУП. Перед постановкой задания и применением результата сверяются подтверждённые названия таблиц и полей последней успешной диагностики текущего подключения. Смена подключения во время загрузки отменяет применение результата.

Источники: `dbo._Reference297` (Сотрудники), `_Reference383` (ФизическиеЛица), `_InfoRg21744` (ТекущиеКадровыеДанныеСотрудников), `_Reference166` (Организации), `_Reference216` (ПодразделенияОрганизаций), `_Reference92` (Должности). SQL не угадывает названия полей и не сопоставляет по ФИО. Признак архива читается из `_Fld30280`, пометка удаления — из `_Marked`. Отсутствие в архиве само по себе не доказывает действующее трудоустройство.

Связь хранится по компании, нормализованным именам сервера/базы и внутренней ссылке сотрудника ЗУП. Повторный запуск обновляет те же записи, даже если изменились ФИО или код. Ручные записи не объединяются автоматически; это отдельное явное действие будущего интерфейса карточки. Для импортированной записи должность связывается с локальным справочником при единственном точном совпадении имени; иначе сохраняется исходное наименование ЗУП без произвольного создания или выбора должности.

Архивные сотрудники также создаются и обновляются, сохраняются неактивными и показываются с пометкой «Уволен / в архиве ЗУП». Счётчик «в том числе уволенных / в архиве» показывает их количество в обработанном пакете. Уже связанные сотрудники при переходе в архив становятся неактивными. Записи, отсутствующие в новой выборке (включая помеченные на удаление в ЗУП), не удаляются и не деактивируются автоматически. Строки другой компании или источника не меняются.

Весь пакет применяется атомарно. Пустой результат, слишком длинные/некорректные поля, повтор внутренней ссылки из-за неоднозначного соединения кадровых данных и ошибки аудита откатывают пакет. Лимит 200 000 строк проверяется после ограниченной выборки TOP (200001); превышение не превращается в частичную загрузку. История задания и аудит содержат только счётчики, исходный служебный JSON результата остаётся в защищённом каталоге обработчика, как результаты диагностики. Результаты импорта исключены из выбора последней диагностики/карты метаданных.

Проверки: `manage.py test apps.accounts.test_one_c_employees apps.accounts.test_one_c_report apps.accounts.test_one_c apps.accounts.test_one_c_jobs apps.accounts.test_one_c_positions apps.accounts.test_one_c_position_schedule apps.resources.test_purge apps.production.test_dispatch` — 57 тестов. Windows-запрос проверяется первым реальным запуском на сервере; в среде разработки проверен контракт очереди и имитированный ответ Windows-обработчика.


Исправление запуска: блок SQL загрузки сотрудников находится внутри ветки реального подключения, сразу после `$connection.Open()`, а не в ветке постановки Windows-задачи. Регрессионная проверка контролирует расположение блока. Фоновый обработчик отдельно проверяет `employees_import=true` в ответе, чтобы обычная диагностика не воспринималась как список сотрудников. Отсутствующий список, неверный формат, пустой результат и превышение лимита теперь имеют разные сообщения. Изменения не вносятся при любой из этих ошибок.


ФИО: справочник физлиц может содержать полное ФИО без заполненных отдельных имени/фамилии. SQL выбирает непустое значение в порядке: `_Reference383._Fld31265` (ФИО), `_Reference383._Description`, `_Reference297._Description`. Полная строка сохраняется в `Employee.zup_full_name` без угадывания её частей и отображается в едином столбце ФИО. Пустые отдельные части не прерывают импорт. Если отсутствуют и части, и полная строка, сотрудник всё равно сохраняется по ссылке ЗУП, показывается служебная подпись с табельным номером и явная пометка «ФИО не заполнено в ЗУП»; вымышленное ФИО в базу не записывается. В истории задания выводятся счётчики неполной разбивки и полностью отсутствующего ФИО. Ручное создание сотрудника по-прежнему требует имени и фамилии. Некорректные типы данных, неверные идентификаторы, неоднозначные кадровые соединения и ошибки транзакции остаются блокирующими.


Карточка сотрудника: `/resources/employees/<id>/`, ручное редактирование `/resources/employees/<id>/update/`. Поля связанных карточек изменяются только синхронизацией. Ручное создание открывает новую карточку; ADMIN, HR_HEAD и PLANNER могут править ручные основные данные. Все запросы ограничены компанией; карточки других компаний возвращают 404.

Должность ищется сначала в текущих данных, затем в последней записи интервальной и обычной кадровой истории не позднее текущего времени, затем по позиции штатного расписания. Везде используется точная ссылка сотрудника, без объединения по физлицу или ФИО. Архивные записи сохраняют последнее известное место работы, источник должности виден в карточке. Будущие кадровые события не выбираются. Пустые интервалы пропускаются. Для дат читается `_YearOffset.Offset`, допускается только единственное смещение 0/2000; незаполненные даты не превращаются в даты рождения. Метаданные всех новых таблиц/полей проверяются до SQL. Запрос сотрудников имеет отдельный ограниченный таймаут 180 секунд.

График берётся из последнего активного неистёкшего назначения на дату загрузки. Плановые суммы берутся из последнего действующего итога ФОТ; при нескольких строках на одну дату суммы не выбираются произвольно. Названия пола, вида договора и вида занятости не угадываются из порядка SQL-перечислений и не показываются без расшифровки. Суммы не подписываются как оклад или фактически выплаченная зарплата.

`Employee.zup_card` содержит только проверенные поля: строки, ISO-даты и десятичные строки, включая явный ноль. Неверный тип/дата/число откатывает импорт; неизвестные поля не сохраняются. В истории задания и аудите только счётчики, в общем списке нет личных данных и оплаты. Версия `employees_card_version=4` не позволяет принять ответ старого обработчика как успешно заполненную карточку. После обновления через админпанель нужно повторить «Загрузить из ЗУП»; обновление файлов само по себе не перечитывает ЗУП.


Список сотрудников по умолчанию показывает только `is_active=True`. Флажок «Показывать уволенных / архивных» включает остальные записи без удаления или изменения данных. Поиск ФИО/табельного номера и фильтр должности объединяются через AND; кириллица сравнивается без учёта регистра и на SQLite. Должность фильтруется по отображаемому значению ЗУП, а при его отсутствии — по локальной должности. Пагинация сохраняет фильтры.

Если новая загрузка оставила должности пустыми, повторение само по себе не доказывает исправление. Формат обработчика v2 считает покрытие кадровых источников для всех и отдельно активных сотрудников: текущая запись/ссылка/соединение должности, интервальная и обычная история, штатное расписание, наличие ссылок в истории исправлений и кадровых приказах, ссылка должности головного сотрудника. Проверка дополнительных источников не выбирает оттуда должность без подтверждения правил отбора и не объединяет трудовые отношения по ФИО/физлицу.

В результате задания доступна ссылка «Скачать проверку кадровых источников (ZIP)» (`accounts:one_c_report?employee_run=<uuid>&format=zip`). Архив содержит один JSON в UTF-8; ZIP используется и по умолчанию для проверки кадровых источников, а явный `format=json` сохраняет доступ к исходному JSON. В файле только число сотрудников и агрегированные счётчики покрытия; имена, табельные номера, должности, документы и зарплата не экспортируются. Скачивание ограничено администратором своей компании. Этот отчёт нужен, чтобы определить реальную причину пустых должностей по данным конкретной базы; структура таблиц сама по себе их заполненность не показывает.


Отчёт проверки из рабочей базы подтвердил: ссылки должности в текущем регистре и выбранных обычной/интервальной историях отсутствуют. Формат v3 добавляет подтверждённый метаданными регистр «ДанныеДляПодбораСотрудников» (`_InfoRg16829`) как источник должности, подразделения и количества ставок. Связь — точная ссылка сотрудника; проверяются пометка удаления, начало/окончание периода и архивный признак. Для активных записей нужен действующий период (последний день включительно), для архивных берётся последнее прошлое место работы. Эквивалентные строки подбора объединяются по кадровым атрибутам; конфликт нескольких вариантов на одну последнюю дату оставляет этот источник неоднозначным, без произвольного выбора должности. Должность может определяться прямо или через позицию штатного расписания. Дата начала записи не подменяет дату приёма. Если выбрана запись подбора, подразделение и ставки берутся из неё.

В проверке появляются `picker_candidate`, `picker_position_join`, `picker_ambiguous`, а также счётчики наличия ссылок в занятости штатных позиций и корпоративном регистре показателей. Эти последние счётчики сами по себе не выбирают кадровые данные. Локальная должность сопоставляется по полному каноническому названию общего справочника, учитывая, что legacy Position.name может быть обрезано до 100 символов.

Поля и связи сверены с исходным отчётом структуры. Реальное покрытие новым источником необходимо подтвердить новой загрузкой на Windows-сервере; получение исходного отчёта не означает, что альтернативный регистр уже проверен на рабочих данных.


Проверка задания `a6fc19fd-a2a5-425f-bae0-7182a778164a` (26.10.2026, 03:10 МСК) показала: подбор находит всех 859 активных сотрудников, но не даёт должности ни одному; у 853 есть непустая ссылка штатной позиции в интервальной занятости (это счётчик наличия, не гарантия действующей должности).

Формат v4 добавляет резервный источник «Занятость позиций штатного расписания»: точная ссылка сотрудника → `_InfoRg40095._Fld40105RRef` → `_Reference394._Fld31540RRef` → `_Reference92`. Подразделение и организация берутся из той же штатной позиции, ставки — из занятости; источник и начало назначения видны в карточке. Основные источники сохраняют приоритет. Наименование самой штатной позиции не выдаётся за название должности.

Для действующих сотрудников выбираются непустые интервалы с положительными ставками, начавшиеся не позже текущего времени, с действующим окончанием и «ДействуетДо» (последний день включительно). Записи с документом назначения подработки/совмещения исключаются. Эквивалентные записи одной позиции с одинаковыми ставками объединяются; несколько разных одновременных вариантов оставляют источник неоднозначным. Для архивных выбирается последняя непустая занятость не позже даты увольнения (если она заполнена) и текущего времени; архивная пометка сохраняется.

Проверка ZIP дополнена счётчиками `occupancy_candidate`, `occupancy_ambiguous`, `occupancy_staffing_join`, `occupancy_position_ref`, `occupancy_position_join`, `occupancy_staffing_named`: они разделяют отбор периода, неоднозначность, связь со штатным расписанием, ссылку должности и её название. До выполнения нового запроса на рабочем Windows-сервере реальное покрытие этого источника не считается подтверждённым. После обновления файлов необходимо один раз загрузить сотрудников заново.


## Формат v5: отображение штатной позиции и точная проверка

ZIP задания `c50fd1b0-9e9e-438f-8bc9-8df5092a3cb9` (26.10.2026, 15:45 МСК) подтвердил: у 852 из 859 активных сотрудников однозначно выбрана штатная позиция, у неё есть наименование и непустая ссылка должности, однако название из отдельного справочника должностей не получено. Этот отчёт не различает отсутствие записи справочника и пустое наименование существующей записи.

Обработчик v5 сохраняет название штатной позиции отдельно, в `zup_card.staffing_position`. Если фактическое название должности не расшифровано, список и карточка показывают штатную позицию с явной пометкой. Она также участвует в фильтре должности. Приоритет остаётся у настоящего названия должности; штатная подпись не разбирается на предполагаемые должность/подразделение и не создаёт связь с локальным справочником Position. В одном порядке отбираются уже выбранная однозначная занятость, штатная позиция подбора, штатная позиция выбранной кадровой истории. Организация, подразделение, положительное количество ставок и дата подписи берутся из выбранного источника; дата не подменяет дату приёма. Правила архивных сотрудников и исключения неоднозначной занятости сохранены.

Общая ZIP-проверка дополнена числом записей/непустых названий справочника должностей, признаками найденной записи должности, подразделения и использования штатной подписи. В карточке ADMIN доступна «Проверка должности (ZIP)» конкретного сотрудника: табельный номер, ссылка сотрудника, время загрузки, состояние, технические ссылки и признаки соединений. ФИО, названия должностей, зарплата и личные реквизиты туда не включаются. Проверка ограничена компанией администратора.

После обновления портала требуется одна новая загрузка сотрудников из ЗУП. Ответ v4 отклоняется, чтобы старый Windows-обработчик не стирал новые сведения. SQL-фрагменты выбора и соединений проверяются на синтетических данных, импорт, фильтры и доступ — тестами Django, карточка — Chromium. Выполнение полного запроса на рабочем SQL Server и фактическое покрытие v5 проверяются последующей загрузкой, а не считаются подтверждёнными этими тестами.


## Уточнение отображения карточки

Раздел «Оплата труда», его ссылка и подготовка денежных значений для шаблона удалены из карточки для всех ролей. Уже сохранённые данные не удаляются; формат импорта этим изменением не меняется.

Пользователь подтвердил формат штатной подписи `Должность /Подразделение/`. При точном соответствии этому формату должность и подразделение отображаются отдельно в списке и карточке. Подразделение из отдельного поля ЗУП имеет приоритет. Исходная штатная подпись сохраняется без изменений, локальная должность автоматически не создаётся. Неполные или иные строки со слешем не разбираются. Фильтр должности ищет только отображаемое название должности. Изменение работает и для ранее загруженных карточек без повторной загрузки из ЗУП.

## Общий справочник должностей из сотрудников ЗУП

После успешного разбора пакета сотрудников импорт пополняет общий справочник `Brigade` и его мост к `Position`. Используется подтверждённое название должности либо выделенная должность из формата `Должность /Подразделение/`. Нераспознанные подписи со слешами и названия длиннее 150 символов не превращаются в предположительные или обрезанные должности. Одинаковые имена объединяются без учёта регистра в пределах компании; разные подразделения не создают разные записи одной должности. Несколько существующих одноимённых записей остаются неоднозначными и не объединяются автоматически.

Существующие ставки, группы, описания и активность справочника сохраняются. Единственная старая Position без связи с общим справочником используется повторно. Сотрудники связываются с единственной соответствующей должностью; архивная отметка сотрудника не меняется. Загрузка каталога и сотрудников выполняется в общей транзакции, результат задания показывает счётчики должностей. Денежные показатели сотрудников в справочник должностей не копируются.

Для уже загруженных карточек ADMIN доступна кнопка «Заполнить из сотрудников ЗУП» в справочнике должностей. Она использует только импортированные карточки текущих сервера/базы своей компании, включая архивных сотрудников, и не запрашивает повторную загрузку Windows-обработчика. Ручные карточки и другие источники исключены. Повторное нажатие не создаёт дубликаты. Последующие загрузки сотрудников пополняют справочник автоматически.
