# Диагностика справочников 1С ЗУП

На Windows-сервере портала откройте PowerShell от имени администратора:

```powershell
cd "C:\Users\dvivanov\Desktop\gpr_system"
git pull --ff-only origin main
.\DIAGNOSE_1C.cmd
```

По умолчанию используется `msk-db`, база `zup`, Windows-аутентификация. Пароли не запрашиваются. Если портал работает под SYSTEM, скрипт создаёт временное задание под SYSTEM и удаляет его после диагностики. Основное задание портала продолжает работать. При доступе к удалённому SQL Server SYSTEM обычно представляется доменной учётной записью компьютера. Ей нужны права чтения базы и видимость метаданных. Если портал запущен под другой учётной записью, запускайте диагностику под ней; скрипт не сохраняет её пароль.

Скрипт выполняет только SELECT: получает структуру таблиц и ищет кандидатов на справочник должностей по совпадениям слов в `_Description`. Проверяется до 5000 строк каждого справочника; выборка может пропустить нужные записи. Совпадения не подтверждают назначение таблицы. Это поиск кандидатов, а не расшифровка конфигурации 1С. Для точного соответствия может потребоваться описание структуры хранения из 1С.

После `DONE` в консоли появятся SQL-учётная запись и таблицы-кандидаты. Отчёт сохраняется в `.runtime\1c-diagnostics\<идентификатор>\report.json`. Он содержит структуру базы, счётчики совпадений и ошибки чтения; значения описаний, записи сотрудников, бинарные метаданные и пароли не выгружаются. Отчёт всё равно содержит внутренние имена сервера и базы, поэтому храните его как служебный файл.

Соединение шифруется с проверкой сертификата. Если SQL использует внутренний сертификат, предпочтительно установить доверенную цепочку на сервере портала. После проверки сертификата администратором можно явно отключить проверку его подлинности на один запуск:

```powershell
.\DIAGNOSE_1C.cmd -TrustServerCertificate
```

Для запуска под текущей Windows-учётной записью вместо учётной записи задания:

```powershell
.\DIAGNOSE_1C.cmd -RunHere
```

Диагностика не изменяет базу ЗУП и справочники портала. Импорт подключается отдельно после подтверждения соответствия таблиц и полей. Синтаксис скрипта проверен автоматически; фактическое подключение и выполнение Планировщиком проверяются на Windows-сервере.

## Запуск из портала

Администратору доступен пункт **«Интеграция с 1С»** в боковом меню (`/accounts/integrations/1c/`). Можно сохранить сервер и базу, поставить диагностику в очередь, увидеть текущий статус, результат и последние 20 запусков. Данные и результаты разделены по компаниям; остальные роли доступа не имеют.

Фоновое задание `YDS Portal` запускает обработчик очереди раз в минуту под своей Windows-учётной записью. Браузер можно закрывать. Интервал диагностики задаётся в минутах: 0 — вручную, минимум для автоматического запуска — 15 минут. Это интервал между запусками, без привязки к времени суток. Пропущенные интервалы не накапливаются. Повторный запуск во время активной диагностики не создаётся. Прерванный запуск помечается ошибкой через 20 минут. После перезагрузки сервера очередь и расписание сохраняются в базе портала.

После первого обновления на эту версию нужно один раз перезапустить основное задание, чтобы загрузился новый фоновый обработчик. В PowerShell администратора, после `ГОТОВО` от обновления:

```powershell
Stop-ScheduledTask -TaskName 'YDS Portal'
Start-ScheduledTask -TaskName 'YDS Portal'
```

Портал будет кратковременно недоступен. Последующие запуски диагностики выполняются в интерфейсе. Для ручного обслуживания очереди доступна команда `python manage.py process_1c`; она работает под текущей Windows-учётной записью. Журнал фонового обработчика: `.runtime\1c-worker.log`.

**Синхронизация справочника должностей ещё не подключена.** Настраиваемое сейчас расписание выполняет только чтение структуры и поиск кандидатов. После проверки соответствия таблиц и полей можно подключить обновление должностей на этой же странице. Диагностика использует ограниченную выборку и не подтверждает метаданные автоматически.

## Читаемые названия и каталог таблиц

В разделе интеграции каталог всех таблиц последней успешной диагностики сгруппирован по типам: справочники, документы, перечисления, регистры, планы и служебные таблицы. Табличные части отмечены отдельно. Поиск работает по названию объекта и SQL-имени; фильтр ограничивает тип, пагинация сохраняет поиск. Стандартные поля, например `_Description`, имеют пояснения без попытки угадывать пользовательские реквизиты.

Новая диагностика пытается прочитать метаданные через существующее SQL-подключение. Из `Params` выбирается только `DBNames`; из `Config` — только файлы UUID объектов, перечисленных в DBNames. Читаемый объект связывается с физической таблицей через UUID и числовой код, реквизиты — через UUID внутри описания своего владельца. Содержимое пользовательских справочников для названий не используется. Чтение таблиц и декодирование выполняются без SQL-записи и без запуска кода конфигурации.

Поддерживается ограниченное подмножество сериализации 1С: UTF-8 или raw Deflate, вложенные коллекции и стандартные заголовки описаний объектов. Это не полный декомпилятор: альтернативные варианты хранения, расширения, ConfigCAS, отдельные типы служебных таблиц могут остаться нераспознанными. Проблемы чтения показываются на странице, неизвестные названия не подменяются догадками. На конкретной базе результат подтверждается новой диагностикой на Windows-сервере.

Служебные бинарные снимки сохраняются только локально в `.runtime\1c-diagnostics\<id>\metadata` для воспроизводимой диагностики. Они содержат метаданные конфигурации, не строки сотрудников или документов. Применены ограничения на файл (8 МБ), общий снимок (128 МБ), число объектов (5000), глубину разбора и время чтения объектов (около трёх минут плюс текущий SQL-запрос). При ограничении чтения результат может быть частичным.

Формат хранения проверялся по описанию и реализации проекта [DaJet](https://github.com/zhichkin/dajet/tree/main/src/dajet-metadata). Реализован самостоятельный ограниченный разборщик; внешняя библиотека не устанавливается.

Дополнительно администратор может импортировать проверенную JSON-карту `tables`: `schema`, `table`, `name`, `columns` (объект физическое поле → читаемое имя). Проверяются наличие таблиц и полей в последней диагностике и повторяющиеся таблицы. Карта относится только к текущему серверу и базе; смена подключения не переносит названия в другую базу. Импорт карт не загружает должности, сотрудников или другие бизнес-данные.

Кнопка **«Прочитать названия (быстро)»** выполняет только чтение SQL-структуры и служебных метаданных. Сканирование описаний всех справочников не повторяется; счётчики кандидатов сохраняются из предыдущего результата и помечаются в интерфейсе. Это позволяет уточнять формат метаданных без полного повторного прохода.

Ошибки Python-разборщика передаются в `reader-error.json`: этап, класс исключения, сообщение и размер DBNames. PowerShell запускает помощник с перенаправлением на уровне процесса, поэтому `$ErrorActionPreference=Stop` не обрывает чтение stderr на первой строке `Traceback`. Если помощник не смог создать структурированный результат, показывается окончание полного журнала ошибки. Это улучшение диагностики не означает автоматическую поддержку любого формата конфигурации.

Повтор UUID в DBNames не считается ошибкой всего файла. Служебный нулевой UUID пропускается, остальные физические привязки сохраняются. Основная таблица выбирается только при единственном совпадении со схемой SQL. Если несколько основных таблиц действительно присутствуют, объект остаётся без названия с предупреждением; обработка других объектов продолжается. Повторные привязки реквизитов сверяются с конкретными SQL-колонками, конфликт разных UUID для одной колонки не скрывается последней записью.

Манифест чтения метаданных имеет корневой объект `objects`, содержащий массив записей. Это исключает особенность Windows PowerShell 5.1, при которой корневой JSON-массив в выражении `@(ConvertFrom-Json ...)` мог превратиться в один элемент-массив, а обращение `.uuid` — сразу в массив UUID. Перед построением пути каждый UUID проверяется как отдельная строка. Сериализация JSON через `-InputObject` сохраняет форму коллекций, включая единственный элемент.


### Переходы по структуре и ссылкам

Названия и SQL-имена таблиц в кандидатах и каталоге открывают отдельную страницу структуры. Страница доступна только администратору своей компании, использует последнюю успешную диагностику текущего сервера и базы; SQL-запросы при навигации не выполняются.

Для ссылочных реквизитов читается описание `Pattern` со ссылочными UUID типов. UUID ссылочного типа связывается с UUID объекта по известным слотам метаданных справочников, документов, перечислений, планов характеристик и счетов, планов обмена, бизнес-процессов и задач. Это разные UUID; совпадение произвольного UUID внутри файла не считается связью. Целью становится только однозначно определённая основная SQL-таблица объекта.

Одна цель открывается нажатием на имя реквизита или SQL-колонку; для нескольких целей показан список выбора. Родитель и владелец табличной части ведут в основную таблицу объекта; владельцы справочника берутся из коллекции владельцев. Нераспознанные типы (в том числе неподдержанные определяемые типы, обобщённые типы и расширения) явно отмечаются; при частичном разрешении показано, что список неполный. Значения строк для определения ссылок не сканируются.

После обновления нажмите **«Прочитать названия (быстро)»**, чтобы дополнить существующую диагностику связями. Прежние результаты без описаний ссылок продолжат открываться, но цели реквизитов будут отмечены как неопределённые. Ручное уточнение названий сохраняет автоматически прочитанные связи.

## Загрузка актуальных должностей

Откройте таблицу «Справочник.Должности» (`dbo._Reference92`) и нажмите «Загрузить актуальные должности». Кнопка доступна администратору, когда метаданные подтверждают таблицу и поле `_Fld25711` как «ИсключенаИзШтатногоРасписания».

Фоновый Windows-обработчик выполняет только SELECT: `_Marked=0x00 AND _Fld25711=0x00`. В портал передаются только `_Description`. Даты ввода/исключения и признак «ВведенаВШтатноеРасписание» не используются: актуальность в этой итерации определяется двумя указанными флагами. Источник 1С не изменяется.

Непустые названия добавляются в общий справочник должностей компании и связываются с должностями экипажей штатным механизмом. Пробелы по краям удаляются; сравнение существующих названий — без учёта регистра. Повторные запуски не создают дублей. Существующие ставки, настройки и активность не меняются; отсутствующие в источнике должности не удаляются и не архивируются. Название длиннее допустимых 150 символов отменяет весь импорт с понятной ошибкой, без обрезки данных.

Результат и ошибки показаны в истории запусков интеграции. Действие фиксируется в аудите. Автоматическое расписание загрузки должностей пока не включено; интервал диагностики по-прежнему запускает только диагностику. После обновления приложения дождитесь перезапуска фонового обработчика.
