# ЯДС портал в фоне на Windows

Один Windows-сервер обслуживает всех пользователей по прежнему адресу, например `http://192.168.70.9:8001/`. Устанавливать что-либо на пользовательские компьютеры не требуется.

Требуются Windows 10/11 или Windows Server 2016 и новее, PowerShell 5.1+, Python, установленный для всех пользователей.

## Первая установка

1. Обновите исходники из `main`. Папка должна быть на локальном диске; оставьте в ней используемый `.env`, базу и файлы. В `.env` укажите `DJANGO_DB_PATH` **к существующей рабочей базе**. При наличии нескольких баз установщик потребует явный `-DatabasePath`, чтобы случайно не выбрать `fresh.sqlite3`. Установщик откажется создавать другую пустую базу.
2. Закройте старое окно `START_GPR` через Ctrl+C: порт 8001 должен освободиться.
3. Нажмите правой кнопкой `INSTALL_GPR_BACKGROUND.cmd` → **Запуск от имени администратора**. Python должен быть установлен для всех пользователей; установщик использует/создаёт `.venv`, устанавливает зависимости и применяет миграции с резервной копией базы.
4. Откройте Планировщик заданий → Библиотека планировщика. Появятся **YDS Portal** и **YDS Portal Update**, оба — «При запуске компьютера», SYSTEM, независимо от входа пользователя. Первый запускается через 15 секунд, второй — через минуту. Установщик сразу запускает портал; проверка обновления также доступна вручную.

`YDS Portal` постоянно имеет состояние **Работает**, результат `0x41301` — это нормально для серверного задания. Закрытые окна и выход пользователя не останавливают портал. `YDS Portal Update` завершается после проверки/обновления; успешный результат — `0x0`.

При другом адресе/порте из PowerShell администратора:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\ops\install-windows.ps1 -Port 8001 -Hosts 192.168.70.9,portal.local -DatabasePath "data\db.sqlite3"
```

Правило Windows Firewall открывает порт только в профилях Domain/Private. Задания не используют пароль входа администратора: они работают от SYSTEM. Доступ AD выполняется прежней сервисной учётной записью из `.env`.

## Если окружение Python было перенесено с другого компьютера

Установщик проверяет запуск `.venv\Scripts\python.exe`. Если он ссылается на отсутствующий Python другого пользователя, установщик ищет рабочий Python: в `venv313`/`venv`, через `py`, PATH и реестр Windows. Сломанное окружение сохраняется под именем `.venv.broken-<время>-<id>`, после чего создаётся новое. `.env`, база и `media` не перемещаются.

Если автоматический поиск не сработал, установите Python 3.13 для всех пользователей или укажите существующий интерпретатор явно:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\ops\install-windows.ps1 -PythonExecutable "C:\Program Files\Python313\python.exe"
```

## Обновления

При каждом включении `YDS Portal Update` проверяет `main` репозитория `Hvidsmen/gpr_systerm`. Для закрытого репозитория администратор добавляет в постоянный `.env` переменную `GPR_UPDATE_TOKEN` — GitHub fine-grained token с **Contents: Read-only** только этого репозитория. Токен не хранится в задании, не передаётся в командной строке и не выводится в журнал.

Нет интернета / GitHub недоступен / токен не настроен: обновление не применяется, старый портал продолжает работать. При новом коммите:

- Код скачивается по конкретному SHA в `.runtime/releases/<sha>`; зависимости устанавливаются в отдельное окружение этой версии. Текущий портал всё это время работает.
- После проверки кода завершаются текущие запросы, портал останавливается, создаётся согласованная копия SQLite и копия `.env` в `.runtime/backups/<UTC-время>/`.
- Применяются миграции; кандидат проверяется на локальном временном порту, закрытом для сетевых пользователей.
- При ошибке миграции/проверки до публичного включения возвращаются предыдущие код и база. При успехе включается новая версия. **После открытия новой версии пользователям база автоматически не откатывается**, чтобы не потерять уже внесённый факт.

База, `.env`, ключ сервера и папка `media` находятся вне папок релизов. Обновление их не заменяет. Личные настройки отчётов и AD-пользователи сохраняются в той же рабочей базе. При первой установке может потребоваться повторный вход из-за перехода на постоянный рабочий ключ сессий.

Проверить/обновить немедленно: `UPDATE_GPR_BACKGROUND.cmd` от имени администратора либо «Выполнить» у задания `YDS Portal Update`. Скрипт показывает этап и время ожидания, дожидается окончания задания и доступности страницы входа, затем выводит зелёное «ГОТОВО. Обновление полностью завершено, портал доступен» и номер версии. При ошибке выводится красное сообщение; сам факт запуска задания успехом обновления не считается. Его триггер можно изменить в стандартном Планировщике. Одновременные обновления блокируются. Сетевой доступ к GitHub/PyPI нужен именно учётной записи SYSTEM; если используется корпоративный прокси, настройте его для задания/сервера.

## Управление и диагностика

- `START_GPR` после установки запускает существующее фоновое задание.
- `STOP_GPR_BACKGROUND.cmd` от администратора запрашивает корректную остановку. Для отключения автозапуска также отключите оба задания в Планировщике. «Завершить» в Планировщике — принудительная остановка; используйте штатный скрипт.
- `.runtime/status.json` — текущий SHA и статус; `.runtime/service.log` — события; `.runtime/worker.log` и `.runtime/http.log` — HTTP-процесс; `.runtime/commands.log` — установка зависимостей и миграции; `.runtime/installer.log` и `.runtime/updater.log` — ошибки соответствующих команд.
- `.runtime` доступна SYSTEM, администраторам и установившему пользователю; содержит чувствительные резервные копии. Она исключена из Git.
- Старые релизы, окружения и резервные копии автоматически не удаляются. За свободным местом и сроком хранения следит администратор.

Портал работает через Waitress; статика отдаётся WhiteNoise. Для совместимости с существующим внутренним HTTP-адресом фоновый режим использует `DEBUG=0`, без перенаправления на HTTPS и secure-cookie. Для внешней публикации нужен отдельный HTTPS-прокси и соответствующая конфигурация.

Реальную регистрацию заданий выполняет установщик на вашем Windows-сервере. Linux-тесты проверяют конфигурацию, архивы, копирование/восстановление SQLite и сценарии переключения, но не заменяют проверку автозапуска после перезагрузки Windows.


## Переключение с ошибочно выбранной базы

Если фоновый запуск сохранил `data/fresh.sqlite3`, а рабочие данные находятся в `data/db.sqlite3`, после обновления исходников откройте терминал администратора в папке приложения:

```powershell
.\SWITCH_GPR_DATABASE.cmd "data\db.sqlite3"
```

Можно передать другой явный путь к существующей базе. Команда проверяет, что это база портала, показывает её проекты, временно отключает триггеры обоих заданий и корректно останавливает сервер. Если обновление уже выполняется, переключение не запускается. До миграций сохраняются согласованные резервные копии текущей и выбранной базы; прежний файл не удаляется. К выбранной базе применяются миграции именно активной версии кода, затем одинаковый абсолютный путь записывается в `.env` и `.runtime/installed.json`. После успеха сервер снова запускается. После смены базы войдите в портал заново.

Если проверка или миграции не проходят, выбранная база и прежние настройки восстанавливаются; автоматического запуска после ошибки нет. Диагностика — `.runtime/control.log` и `.runtime/commands.log`. При прерывании переключения незавершённое состояние восстанавливается до следующего старта сервера. Настройки AD и остальные строки `.env` сохраняются.
