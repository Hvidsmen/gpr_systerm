# Подготовка тестового обновления до остановки HTTP

Диагностический признак: зависимости уже установлены, резервная копия завершена и создан `candidate-*.json`, но первая проверка Django ещё не вывела результат. Старый `run_manage` мог ждать до 1800 секунд и наследовал ввод supervisor. Браузер при отключённом HTTP показывал последний полученный этап скачивания. Это не означает, что скачивание продолжается. Точная блокирующая операция в конкретной установке определяется стеком проверки; отсутствие вывода само по себе не доказывает причину зависания.

Новый порядок обновления версии:

1. Скачать точный SHA.
2. Пока установленный тест обслуживает запросы, создать отдельное окружение, установить фиксированные зависимости и выполнить `check` новой версии. Конфигурация кандидата отдельная, указатель установленной версии не меняется.
3. Только после успешной проверки остановить принадлежащий supervisor HTTP-процесс.
4. Сделать снимок последних тестовых данных, применить миграции и подготовить статические файлы, затем опубликовать указатель версии.
5. Запустить и проверить выбранную версию.

Полоса показывает шесть этапов, включая подготовку без остановки. Во время подготовки обычный статус обновления доступен через работающий тестовый HTTP; детали текущей операции записываются в состояние задания и `.runtime/prepare.log`. Миграции сохраняют прежний механизм резервной копии и отката. Снимок делается после остановки, поэтому сохраняет изменения пользователей, внесённые во время подготовки.

Управляющие команды запускаются через отдельный runner с `-I -u`, правильным каталогом выбранного кода и закрытым вводом. Исключение — явно переданный секрет для подготовки копии: он передаётся через закрываемый pipe, без записи значения в аргументы или журнал. Через 30 секунд runner пишет стек Python без локальных переменных; `check` ограничен 120 секундами. При тайм-ауте завершается только созданное дерево процесса. Бюджеты миграций и статических файлов не увеличены.

Ошибка подготовки не останавливает выбранный HTTP и не начинает миграции. Неполный новый релиз удаляется, если не выбран в манифесте; заблокированный каталог сохраняется для диагностики. Изменение манифеста после подготовки или несовпадение конфигурации кандидата не допускают установки. Рабочий портал и его задачи не останавливаются и не обновляются.

Для уже зависшей старой версии сначала нужен результат её диагностики или завершение задания. Однократный `repair-staging.ps1` из точного SHA исправления использует новый runner. Он отказывается вмешиваться в активное обновление или незавершённое восстановление базы; вручную менять состояние задания и удалять маркеры восстановления не требуется.

Проверки покрывают закрытый ввод и отдельную передачу секрета, дамп стека и завершение собственного процесса, подготовку при занятом HTTP-lock, сохранение записей между подготовкой и остановкой, откат миграций и отказ при изменённом кандидате. Интеграция `STAGING_BROWSER_TESTS=1 STAGING_WEB_RELEASE_TESTS=1` проходит настоящий цикл кнопки обновления с новым venv, миграциями и перезапуском; `STAGING_PROGRESS_BROWSER_TESTS=1` проверяет шесть этапов, разрыв связи, восстановление, ошибку и мобильное отображение.
